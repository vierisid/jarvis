# ON-B-07: first-workflow intent validation

Default-off `activation-intent.v1`, with no onboarding provider dependencies.
The factory is inert. B11 owns binding `intent.validate`; this module adds no
daemon route, legacy handler change, model, planner, job store or workflow write.
Its catalog entry is generated by the existing B11 script.

## Input and outcomes

Call `createActivationIntentProvider(deps).validate(context, submission, signal)`
only for an explicit Create action. A submission contains `action: 'create'`,
`request: { schemaVersion: 1, requestId, intentVersion: 1, prompt, contextRefs }`
and `answers: Record<string, string>`. This is the U07 request plus its separate
clarification answers; the host strips its own view/journey routing envelope.
Each selected reference is `{ kind, id }`, never a token, URL to fetch, tool
grant or client-selected actor/project. Reference kinds are provider-owned;
the canonical resolver decides which ones it supports. Unknown selections are
unavailable, never replaced with a guessed source.

The original prompt, whitespace, Unicode and answers remain intact. The prompt
limit matches U07's 2,000 characters. The envelope is bounded to 32 KiB, with
20 references, 20 answers of at most 2,000 characters, and 20 assessment issues.
Malformed/unknown fields and versions are rejected rather than discarded.
Blank/overlong prompts within the envelope bound return `invalid` with their
original text. On transport or envelope failure the host retains its local draft.

Available validation yields `invalid`, `needs_input`, `unsupported`, or `ready`.
Only `ready` contains an intent. Missing details/connections and unsupported
nodes are blocking. A trusted assessment can explicitly identify a legitimate
`placeholder`; it must supply a label/message explaining what remains unresolved.
That yields a qualified **disabled draft intent**, never runnable readiness.
`activationFeedback` (browser-safe direct import from `feedback.ts`) returns a
patch to merge into U07's existing model, preserving correction fields when a
temporary failure omits `issues`. Service failures/cancellation permit an explicit
retry; disabled, missing, unsupported or unauthorized capabilities remain blocked.
Overlong answers within the envelope limit return editable `invalid` field errors
without truncating text. The owning host preserves the draft and advances its
feedback revision. Validation never reports U07's
`accepted` phase, which belongs to an actual B08 job acknowledgement.

Unavailable reference issues carry the exact user-selected `{ kind, id }`. U07
offers an explicit Remove selection action for that reference; it only edits the
draft, retains other selections/answers and is disabled during pending requests.
Removing a selection does not validate, grant access or create work. A subsequent
Create rechecks the remaining request and can still require replacement data.
Assessment services cannot supply reference-removal metadata or select sources.

## Existing service boundary

`authorize` derives actor/project from live server authentication. `servicesFor`
selects an immutable scope-bound service binding; its ID changes when the backing
store/account selection changes. `access` checks actual draft-creation access,
`resolve` verifies every explicitly selected reference and returns its scope,
exact identity and revision, and `assess` supplies the existing composition
service's read-only missing-input/capability assessment. These are mandatory
production bindings: there is no heuristic/example classifier, permissive
default assessment, or production fixture fallback. Missing bindings remain
unsupported. Assessment must not execute composition or create a journal/job.

The current core composer preserves wording in `WorkflowJobSpecification` and
performs graph/capability checks during composition. B09 must reuse that path;
B07 deliberately does not run a second planner. The host still needs to supply
a verified read-only assessment binding before enabling this capability. The
deterministic assessment in tests is evidence for the protocol, not a claim
that a new general-purpose semantic assessor is deployed.

Reference contents/credentials are not copied into the intent. Clarification
answers are user data, not proof of connection or tool access. Scoped services
must keep external text in the existing untrusted-content framing if their
assessment crosses a model boundary; no string can alter the creation policy.
Authorization, binding identity and access are rechecked across awaited work;
selected reference revisions are checked again after assessment. Errors expose
only bounded reason codes, never service exceptions.

## Handoff to creation

`requestDigest` binds the exact versioned request and answers (object key order
does not matter). `intentId` additionally binds server scope, binding generation,
verified reference revisions and qualifications. Identical inputs against the
same observations reproduce these identities. A changed answer/source revision
cannot silently retain the same intent identity.

B07 is stateless: it does not claim to reject reused request keys across calls.
B08 owns durable same-key/same-body replay and changed-body conflicts. Before
accepting/using a serialized intent, B08/B09 must call the provider again with
the original submission under live scope; a client `ready` object or digest is
not an authorization token. Preserve the original request and answers in the
durable job. Resolve references through authorized canonical readers, and carry
qualifications to composition and the result. Do not concatenate raw external
text into a privileged prompt or turn a reference into an inferred goal link.

The immutable creation policy permits only a saved disabled draft: no publish,
enable, run, tool grant or goal association. B09/B10 must verify that actual
saved artifact. This validator has no mutation port and cannot create a job,
send a message, start OAuth, or perform native/browser effects.

## Verification and rollback

`bun test src/onboarding-next/activation-intent` submits all three existing U07
examples with/without required fixture data and checks edited wording, missing
Google, notes/sources, unsupported nodes, qualified placeholders, hostile text,
scope/revocation races and module absence. Clicking an example only edits text.
Tests exercise actual U07 and B11; U10 coverage runs when its source is present.
Other capabilities, release approval, reference readers and assessment are
deterministic fixtures. Native/provider/model and full D/F/Q release evidence
remain separate prerequisites; no live account actions are performed here.

The approved U07 view is reused without redesign (onboarding checkpoint
`2410205462365531104`, activation node `1097:48090`). Rollback removes/disables
this provider/binding and regenerates the catalog. There is no new table to
drop; retain journey, request and workflow/draft records and the legacy handler.
