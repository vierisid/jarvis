# A6: bind workflow machine and connection session

## Contract

The first machine operation selects one computer for the run. Subsequent
machine operations use the same computer and the same daemon-owned connection
generation. A missing capability, disconnect, revocation, reconnect or explicit
different target cannot silently choose a replacement. Ordinary chat routing
retains its existing behavior.

The selected approach is a durable binding with a dispatch fence. An in-memory
choice would lose the relation on restart; per-step targets preserve individual
approvals but do not stop the next step choosing another computer. Requiring
every workflow author to specify every target would leave delegated tools and
existing unbound workflows exposed.

`workflow_run_machine_binding` has one row per `flow_run`, inserted within an
immediate SQLite transaction and deleted with its run. The public run response
adds nullable `machineBinding`:

```ts
type RunMachineBinding = {
  runId: string;
  sidecarId: string | null; // null means the daemon's local host
  sessionId: string | null; // null means no verifiable connection at selection
  selectedBy: 'implicit' | 'explicit';
  boundAt: number;          // epoch milliseconds
};
```

Binding is lazy: workflows that never access a machine do not need one. The
first capable connected sidecar remains the default, with the existing local
fallback when permitted. Local selection also stays pinned when a sidecar later
connects. Explicit names must identify exactly one device, then become stable
IDs. Concurrent first steps cannot install different bindings for one run.

The sidecar session ID identifies the exact control socket, is generated by the
daemon, and is never accepted from model arguments or sidecar registration.
Reconnecting the same machine creates a new generation and blocks continuation.
Local sessions identify the current daemon process. A daemon restart therefore
retains the binding while invalidating the connection assumptions. This is a
conservative connection fence, not proof of OS login identity or unchanged UI
content within a connection.

## Enforcement and receipts

- The sandbox tool and delegated-agent backends establish an asynchronous scope
  carrying the run/project identity. Concurrent runs and chat do not share it.
- Bounded tool preparation pins the computer before creating an Authority
  approval. The effect's target includes the binding and required capability.
- Tool target selection and the sidecar routing helper enforce that binding.
  The manager repeats the machine/session check synchronously before sending
  RPCs and notifications on the socket, after the existing execution checkpoint.
- A pre-dispatch failure records `blocked` with `effect: 'not_started'`. Earlier
  successful receipts remain successful, including a late result from an action
  that already started. Stored terminal effects are returned without redispatch.
- M7 retains its per-tool Authority checks. A delegated loop receives the blocked
  tool error and cannot move its subsequent call to another computer. Its final
  narrative is not independent verification of the tool's business outcome.

Failure codes are `WORKFLOW_MACHINE_OFFLINE`, `WORKFLOW_SESSION_CHANGED`,
`WORKFLOW_CAPABILITY_UNAVAILABLE`, `WORKFLOW_RETARGET_REQUIRED`,
`WORKFLOW_TARGET_AMBIGUOUS`, `WORKFLOW_MACHINE_UNAVAILABLE`,
`WORKFLOW_BINDING_IDENTITY`, `WORKFLOW_BINDING_LEGACY` and
`WORKFLOW_SAMPLE_BINDING_UNKNOWN`. They use A2's shared `ActionOutcomeError` shape.
Main's existing sandbox error handling fails the step honestly. With A2 merged,
the API exposes typed outcomes and its explicit probe option can branch on them.
A probe's handler must not itself require the unavailable computer.

## Retargeting, previews and recovery

There is no in-place retarget or automatic retry. Review completed/uncertain
effects, choose the explicit computer for a new run and obtain fresh approvals.
This includes workflows that previously used distinct explicit computers in
one run: a run now has one machine. Separate reviewed runs are required for
different machines. Do not restart completed business work just to recover a
machine binding failure.

Old machine effect receipts and old delegated executions have no verifiable
session. They cannot acquire a replacement binding on upgrade. New delegated
receipts carry a binding-contract marker so their first machine call can bind
after the delegation request was recorded.

Saved preview outputs lack trusted session provenance. A UI preview whose input
references those outputs must run the required perception steps again in a full
run. The guard checks the dispatching step's expressions and frozen input
override, including nested and loop-derived references. It conservatively checks
both conditional branches; arbitrary provenance fields inside sample JSON do not
establish trust. Unrelated samples, the tested step's own auto-captured output,
literal previews and current trigger payloads do not block fresh perception.
Non-UI previews retain their existing behavior. No earlier approval, machine
binding or test receipt is copied to a newly created run. Same-session
pause/resume retains the existing binding. A connection change requires fresh
review and perception.
