# D-01: Brief entry and room boundary

The Brief dashboard can now be developed without replacing the released dashboard. The normal URL still renders `AppShellV2`. The only existing application file changed is `ui/src/main.tsx`, which mounts the entry boundary around that same element.

## Quick verification

From this worktree, run `bun run build:ui`, then `python3 -m http.server 4381 --bind 127.0.0.1 --directory ui/dist`. Use a different unused port in another worktree.

1. Open `http://localhost:4381/?brief=preview#/_brief_preview`.
2. The page says **Isolated development preview**, rather than showing a sample business dashboard.
3. Toggle sidebar state, chat state and Light/Dark. The visible values change; no brain, voice, workflow API or WebSocket is started by this preview. These are state checks, not the future animated layout.
4. On a normally running, already-onboarded Jarvis brain, `?brief=1#/brief/today` shows the unavailable room notice. **Open current dashboard** removes only the Brief flag and returns to the existing application.
5. Without the opt-in, existing room, standalone panel, task, answer and developer hashes retain their owner. The static preview server has no backend, so it is not a live-dashboard test server.

## Ownership and integration

This is the D foundation. F owns domain contracts, capability readiness and behavior; Q owns core reliability. No API route, schema, workflow engine, writer, hosted account or production default changes here.

- `entry/route.ts` owns the exact URL gates and allowlisted source-ID selection. Unknown destinations return to the current app. An `onboarding` query takes precedence so the current reset/resume handler remains the owner.
- `entry/DashboardEntry.tsx` chooses one root. Normal Brief destinations use the existing onboarding gate; the explicitly isolated developer preview bypasses it and does not instantiate live hooks. No new thread, voice or socket provider belongs in this boundary.
- `contracts.ts` contains presentation ports. It does not freeze the F-01 business schema. Keep source IDs, unavailable and empty states distinct; do not infer successful data from a missing provider.
- Each `rooms/<id>/registration.ts` is independently owned by its room task. The registry imports registrations without requiring unfinished feature modules. Shared registry or entry changes need one integration owner.
- `adapters/view.tsx` binds a room-local read hook to a typed component. The live host refuses to display a fixture view as business data. This is a presentation guard, not a security boundary or a substitute for provider authorization.
- `components/controls.tsx` reuses the existing Button. D-03 owns its refinements; D-02 owns the approved tokens and materials. The small foundation stylesheet is scoped and does not restyle v2.

## Adding a room in a later PR

Create the view type and read adapter inside the owning room directory. Return an explicit `unsupported` or `unavailable` result until the provider and activation gate are ready. Bind the room component with `bindBriefView`, then assign the resulting `Body` in that room's existing registration. Keep one live connection owner; do not start a second thread or voice connection to populate a room.

Use `shell.route.selection` for source identities and `shell.navigate` for Brief navigation. Shell appearance, sidebar and chat state live above the room component and survive room navigation. Room-local selections, drafts, scroll restoration and conversation persistence are the later owning tasks, not claims of this foundation.

The explicit preview is `mode: "preview"`. Any later sample dataset must remain clearly marked and confined to that mode. It must never become the fallback for missing live data.
