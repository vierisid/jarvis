# D-27 — Connected workspace and service setup

D-27 adds the optional Connected room: compact device/service rows, a searchable catalog, consistent service identity through setup and completion, cancel/expiry/reconnect states, and exact device management handoffs. Device status remains visible without a hosted-brain card, old settings tabs or a generic offline footer.

This card is delivered for review, **not activated**. The production registry and capability defaults are unchanged. Merge prerequisite: D-01. Live activation requires integrated and verified **F-22 and F-25**, with both `connections` and `navigationCompatibility` ready and enabled. D-28 is outside this PR.

## Contract integration

F-22 #943 appeared during implementation. Its contracts and actual headless setup module were inspected at `9f5b258e8548cd3b481c17b5a1653b20753206a2`; D-27 uses a structural, injected bridge in `f22-adapter.ts`, with no import from that unmerged branch.

An integration host supplies `createF22ConnectionsPort(scopeId, binding)` with:

- `read`: the authenticated F-22 v1 result, scoped by the server. Partial source failures stay explicit; unavailable is never an empty success. No account email is inferred from a stored ID.
- `createSetup: (scope, ports) => new ConnectionSetup(scope, ports)` using F-22's real export and per-tab `sessionStorage`. That adapter owns persistence, local nonce validation and the ten-minute expiry. D-27 does not introduce backend start/resume/cancel endpoints.
- `openSetup: openLegacyConnectionSetup`. These existing settings and workflow forms own browser OAuth, channel configuration and manual piece credentials. Even OAuth-shaped piece values currently use the existing manual form. The browser fixture's sample catalog is design data, not a promise of live integrations.
- F-25 device destinations and optional verified update metadata. Update/revoke/enrollment buttons only navigate to the existing management owner; D-27 does not execute those effects. Missing update metadata remains unreported and cannot enable an update action.

Retain the controller per authenticated scope and retire it on logout or replacement. Register with `connectionsRegistration(useBinding)` only after both activation gates are met. Missing bindings return unsupported; fixture accounts cannot enter the live shell.

F-22 persists before opening its setup surface. A remount/reload restores the attempt, catalog search and return scroll without reopening setup. Explicit reopening does not create another attempt. Cancellation or scope loss invalidates pending reads. Failed/lost responses remain uncertain until checked; a verified failure to persist/open permits an explicit retry.

A focus/browser return only triggers a read. New-account verification asks the user to select the canonical account, so an unrelated pre-existing account cannot complete the flow automatically. Reconnect binds the exact original account. A connected result is rechecked against a fresh canonical projection before the controller publishes success. Saved credentials produce **Credentials saved / Configured · not verified**, never Connected. Library installation remains separate from authentication.

## Verification

Bun **1.3.14** matches the branch CI pin; the frozen lockfile install passed without lockfile changes. Exact counts, commands and evidence are in [D-27.json](D-27.json).

Tests cover public-field projection, scope/permission failures, duplicate and uncertain setup, late responses, exact-account confirmation, cancel/expiry/reload, device handoffs, UI search/scroll/focus, eight shell combinations and configured versus authenticated state. The optional integration suite ran against F-22's actual published `ConnectionSetup`, using fake canonical snapshots and disposable in-memory storage. No real service account, credential write, OAuth grant or device effect was invoked.

To run those cross-stack tests from a checkout containing the pinned Git object:

```bash
export PATH="$HOME/.local/share/jarvis-toolchains/bun-1.3.14/bin:$PATH"
D27_F22_DIR=$(mktemp -d)
mkdir -p "$D27_F22_DIR/ui/src/brief/connections" "$D27_F22_DIR/ui/src/lib"
git show 9f5b258e8548cd3b481c17b5a1653b20753206a2:ui/src/brief/connections/setup.ts > "$D27_F22_DIR/ui/src/brief/connections/setup.ts"
git show 9f5b258e8548cd3b481c17b5a1653b20753206a2:ui/src/lib/uuid.ts > "$D27_F22_DIR/ui/src/lib/uuid.ts"
D27_F22_SETUP_MODULE="$D27_F22_DIR/ui/src/brief/connections/setup.ts" bun test ui/src/brief/connections
```

Without that optional module, cross-stack cases are explicitly skipped; local projection, controller and React tests still run. This does not certify the combined deployed stacks or the real authenticated route, whose own tests belong to F-22.
