# D-08: Local decision confirmation and stack advancement

Implemented 5 October 2026. This PR is stacked on corrected D-07 (`c3a981d2`), targets `brief/d-07`, and stays unmerged. Worktree: `/home/vierisid/.cache/codex/jarvis-d-08`. Inspected main: `2c70cf0f`. The released dashboard and default Today registration remain unchanged.

## What changes

D-07 presented and dispatched a reviewed decision but had no local completion sequence. D-08 retains that same paper while its owner resolves the request. Only a correlated, authoritative receipt can confirm it. Confirmation lasts 380ms at the actual pressed pose, followed by a 220ms inward settlement. The latest owner-provided next item enters the same slot over 220ms; only then do its summary and count appear. No mount or navigation count-up is added.

Approval says **Execution confirmed**, in green, only for a committed effect. **Draft kept · Nothing sent** is neutral. **Rejected · Nothing sent** uses the error accent. Reject stays in the explicit Review path. Failed, conflicting and unknown outcomes retain the original decision and offer refresh rather than optimistic removal or automatic retry. A refreshed conflict requires reviewing its new revision. Goal insertion does not replace the current paper.

Quick presses freeze an unfinished hover at its painted position. Repeated clicks are locked synchronously before the owner renders pending. The next identity gets a fresh hover/review lifecycle. Completing an expanded review restores its previous main scroll position. Focus follows the next Review control, unless the user moved to another control meanwhile. Reduced motion removes travel, retaining the readable confirmation and identical outcome.

## Review quickly

Open `http://localhost:4388/?brief=preview&specimen=today#/_brief_preview` with the dedicated static server running.

1. Hover the paper and press **Approve & send**. The sample owner waits 650ms, confirms on the same paper, then advances to **Investor update**, two actions to one.
2. **Reset example**, then **Keep draft**. Reset again, **Review follow-up → Reject**. Compare the local receipts and contours.
3. **Append goal step** keeps the follow-up in front. Resolve it and the investor update; **Pilot invitation** reaches the front, supports re-hover/review and can be resolved again.
4. Choose **failed** or **unknown** in **Simulated operation result**. Act, then **Reload authoritative view**. The affected decision stays visible; there is no second send or success animation. This remount retains the fixture owner's projection, not a real network/browser restart.
5. Choose **conflict**, act, then **Refresh decisions**. Review the updated date before acting on the new revision. Change the result to **confirmed** to complete it.
6. Check Light/Dark, rail/expanded, Pebble open/closed, the 390px review width, a long document and Reduce motion. Supporting cards/chat remain D-07 layout fixtures for later tasks.

No example sends email, runs a workflow, or calls a live provider. Reset, simulation and append controls exist only in the explicit isolated preview.

## Integration contract for F-12 / F-14

Owned source: `ui/src/brief/today/decision-transition/`. Minimal integration touches D-07's paper, binding, preview and existing isolation test. D-01's Today slot and D-07's optional registration factory stay intact. There is no queue store, persistence, endpoint, polling owner or backend mutation in D-08.

`DecisionBinding.onAction(decision, action, requestId)` is still the sole dispatch seam. The optional third argument is an opaque correlation token generated with `getRandomValues`, including on HTTP self-hosted origins. **It is not durable server idempotency.** F-14 must enforce exact revision, permission and durable effect/idempotency rules. Returning/resolving the callback is never interpreted as completion. A thrown/rejected callback becomes a blocked uncertain result.

The owner publishes `binding.operation` and `binding.state` from its canonical write/read/reconciliation path:

```ts
// Acknowledgment while the owner works:
{ decisionId, revision, requestId, state: "pending" }

// Only after an authoritative matching result:
{ decisionId, revision, requestId, state: "confirmed", action: "approve", effect: "committed" }
{ decisionId, revision, requestId, state: "confirmed", action: "keep_draft", effect: "not_started" }
{ decisionId, revision, requestId, state: "confirmed", action: "reject", effect: "not_started" }

// Fail closed; optional human-readable error message:
{ decisionId, revision, requestId, state: "error" | "conflict" | "unknown", message }
```

These are presentation types, not a new HTTP response schema. Echo the original decision ID, reviewed revision, requested action and attempt token. An approved permission without a committed execution is insufficient for an approval completion. For Keep draft/Reject, the owner must establish the non-execution result; do not infer “Nothing sent” from an HTTP 200. Unsafe combinations are blocked. Failed/unknown/blocked canonical projections take precedence over an inconsistent success receipt.

The controller retains **one outgoing visual snapshot**, not an independent queue. The owner must keep the current decision at the front when appending work and supply the actual next front/count after resolution. A confirmed receipt can arrive before the refreshed queue: D-08 waits for a ready different decision ID or an explicit empty result. Loading/stale/unavailable are not empty. If a newer failure arrives before handoff, settlement stops. Keep the current receipt until the next attempt; do not replace it with an unrelated operation before this view can observe it.

On conflict, publish the refreshed same decision with a new revision while retaining the matched conflict receipt. The old review is discarded and the new version can be reviewed. Unknown/failed effects stay blocked until the owner reconciles them; D-08 does not invent a retry policy. After reload, render the canonical unresolved projection with its truthful approval/outcome/actions and existing pending/unknown operation where applicable. Historical receipts do not replay a new completion. Capability loss clears held artwork. No async failure after unmount can alter a later document.

Activation requires **D-07, F-12, F-14**, existing navigation compatibility gates and release approval through D-33. The API integration, restart/reconnect durability and real effect receipts must be verified with those owners before activation. Do not wire this to the legacy approve endpoint merely because its request returned successfully.
