## Release assessment and activation matrix

`assessRelease` accepts a versioned saved release record, a capability snapshot and an explicit runtime identity. Unknown/missing records, unknown capabilities, duplicate card entries, wrong repositories, mismatched runtime revision/environment, unmerged prerequisites or incomplete checks block the release. A hosted candidate additionally needs the exact hosting commit and a passing `hosted_pair` check bound to **both** brain and hosting commits. A previous-binary rollback also requires separate `binary_rollback` evidence.

## Integration contract and evidence ownership

The release owner supplies `BriefReleaseCapabilities(registrations, requestedIds, runtime, readRecord)` to the same authenticated capability/API routes and shared chat transport. It extends the F-01 registry, retains exact provider-identity checks and re-reads both the saved record and live provider readiness on every snapshot. Missing or failed record reads fail closed. Detailed reasons are available from `assessment()`; the browser protocol retains its existing fixed dependency-not-ready reason.

This opt-in registry is **not wired into the existing daemon in this card**. The existing F-01 constructor and independent module flags keep their existing behavior. D-33/release assembly must choose the gated registry for all Brief consumers, prove canonical providers and identity/session lifecycle are connected, and record `host_bindings` evidence. The checked-in record marks this blocked. Running the audit command does not install a gate into an already running daemon. D-33 separately requires live candidate-bound D-32/F-28/Q-22 evidence, exact UI/brain/hosting/sidecar/schema/flag combinations and team approval. This source receipt cannot be used as its passed live F-28 gate.

The record is operator-owned evidence, not signed attestation or a GitHub client. A release owner must recheck merged commits against the selected runtime, refresh the inventory, and supply truthful test results and provider snapshots. A string saying `passed` is not independent proof. Required checks are `fresh`, `upgrade`, `old_client`, `flag_rollback` and `host_bindings`, all tied to the selected runtime revision. Hosted evidence also names the hosting revision. `ready` means technically eligible under those supplied inputs; `deploymentAuthorized` is always false and this module performs no deployment.

[F-28-release.json](F-28-release.json) records the F-27 source-stack revision used for this inventory. It is deliberately not a release approval for the eventual F-28 commit or a merged runtime. Its candidate checks are not-run/blocked, `approvedCapabilities` and observed `activeCapabilities` are empty, and `releaseEnabled` is false. Local source test results live separately in [F-28.json](F-28.json). Do not replace candidate checks with these local results or infer production state from fixture tests.

## Migration and compatibility evidence

Tests use new temporary SQLite files and real vault/workflow/provider migration functions. No migration or destructive down migration is added. The fixture generator uses pinned repository objects, records SHA-256 provenance and reproduces all five fixture files byte-for-byte. Checked-in fixtures contain schema and historical conversation code only; tests do not need Git, a server or network access.

The suite exercises fresh databases, the roadmap baseline, current main, and populated partial F-07/F-20 schemas. It inventories all **34** new F tables, checks every original table column survives, checks the added ingredient/draft-pin/replay-source fields, and seeds every added table. Histories, saved titles, flow/version/run IDs, measured-goal values, placement/order, composition ingredients, attachment identities, document revisions, idempotency receipts, forget suppression and removal metadata survive close/reopen and disabled release capabilities. A legacy score does not become a fabricated measurement. Persistent removal triggers reject old raw-writer reactivation/deletion. Foreign-key and SQLite integrity checks pass.

Byte-for-byte conversation reader/writer code from both pinned historical revisions reads the upgraded database, creates a new legacy conversation and writes a message. Re-upgrade adopts its tab without losing saved metadata or any prior Brief table rows. This is actual historical conversation-code compatibility, not full historical-daemon certification. Existing old-client/new-server API refusal tests and unknown-major snapshot checks also run; a gated API returns 503 without calling its provider.

Full binary downgrade after using new guarded data remains **unsupported without separate evidence**. Old runtime code may lack ingredient pins, edited-document approval fences, measurement semantics, forget suppression or manual-run receipt checks even when it can read SQLite. The safe supported rollback is to disable the affected capability on guard-aware code while retaining all additive schema and histories. F-24 adds a read-only hosting contract rather than a local F schema; no real hosted pair or production account mutation was exercised here.
