# D-21 · Workflow management and local removal

All workflows now has separate targets for opening a workflow, changing activation and deleting it. Inline confirmation affects one identity. Acknowledged removal closes that row’s gap; receipt-backed Undo returns the same workflow to its original slot, paused. Failed enable keeps the acknowledged value and exposes its blocker.

This is an optional presentation module and an isolated fixture preview. It is **not activated in production**. F-20 is not present in this stack or the fetched branch inventory. The legacy irreversible DELETE route is never called, wrapped or advertised as reversible.

## Design and behavior

Approved native source: [All workflows, 255:3795](https://www.figma.com/design/eNfKeirIKLZLlZEasrurZa/Jarvis-Brief-Working-design?node-id=255-3795), page 81:2, UI-35 final checkpoint. Saved UI-25 native Light/Dark exports and inline confirmation were inspected, not an older HTML mockup. `figma-reference.json` pins their hashes and bounded differences.

The name cell opens its exact flow/version. Switch and bin are siblings, so neither can trigger row navigation. Status is always Enabled/Paused; publication and readiness stay separate. A switch changes only after acknowledgement. Each command captures owner, flow, version, expected revision and request ID; replies are validated before they affect the view. Different rows can resolve independently; duplicate presses cannot create concurrent commands for the same row.

Cancel and Escape do not mutate. Delete is confirmed inside the same row; the gap collapses over the shared 280ms timing only after acknowledgement. Multiple tombstones reserve their original slots even when Undo is used in reverse order. The restored item must be DISABLED with the same flow/version. Expired or refused receipts cannot restore a local fake. A lost or malformed response leaves the affected row locked with Check result, which reads that exact durable request and never resubmits it.

Navigation, shell reflow and theme changes retain the same controller owner. The list has independent scrolling and a bounded Undo area, preserving access without covering another row or the corner Pebble. Focus follows Cancel, deletion and restoration only if the user still owns that row; late acknowledgements do not interrupt typing elsewhere. Reduced motion uses immediate gap placement.

## F-20 and host activation handoff

1. Register `workflowManagementRegistration(useBinding)` only after an authenticated provider is ready and `workflowRemoval` is explicitly supported/ready/enabled. Binding source and scope must match the controller. Missing/mismatched bindings fail closed without reading fixture data. The default production registry remains unchanged.
2. Supply a **complete** authorized `WorkflowList`, in stable initial order. A ready snapshot is authoritative over settled local commands; cached snapshots that may predate an acknowledged mutation must be marked stale. Do not map the legacy list endpoint’s first 100 rows to an alleged complete collection. Aggregate pagination or extend the adapter contract before live registration. Map ENABLED/DISABLED to the switch, and DRAFT/LOCKED/publication/readiness to separate facts. Unknown readiness is not Ready and absent history must be qualified by the provider.
3. `change` must persist request identity before dispatch, authorize scope, compare the revision/version, and return a matching acknowledgement. Rejected means no command mutation committed; an acknowledgement timeout or unknown transport result must throw or return pending. The UI then retains the lock. Mutation rights/revocation remain server-enforced.
4. Remove only through F-20’s reversible removal service. It atomically stops future triggers, retains flow/version/run evidence and returns a bounded, scoped receipt. Restore must validate that receipt, restore the exact identity **paused**, and never replay a run or external effect. In-flight work behavior and trigger reconciliation remain F-20’s responsibility.
5. `reconcile` is a read of the original request ID, not a retry endpoint. The host must retain/recover durable pending commands and removal receipts across reload/reconnect before live activation. This module’s controller preserves state across mounted room changes, not browser reload. The F-20 persisted receipt/recovery hydration contract is still an integration gate; there is no invented backend endpoint or claim of reload-safe Undo here.
6. Keep one controller per authenticated scope; retain it across room navigation and retire it on logout/owner replacement. Creation keeps its separate draft/scroll owner. Route name clicks to the exact graph and return to this list controller. Rebind sidebar counts to the same real collection; the specimen’s shell badges are illustrative, not an outcome provider.
7. Test the final F-20 adapter, auth, stale-revision refusal, trigger removal, reload recovery, receipt expiry and restoration against real isolated backend data before enabling. Follow D-33 release gates. This PR does not prove F-20 runtime behavior.

## Review corrections: R1 and R2

- R1: a fresh list can restore an externally restored workflow into its reserved slot, with its current activation/revision and no obsolete Undo receipt. A stale pre-deletion snapshot cannot resurrect it; a workflow still absent from fresh data retains its receipt and Undo opportunity. Refresh never bypasses an unresolved command lock.
- R2: fresh list data replaces transient action feedback, preventing an Enabled switch beside “Workflow paused” or an already resolved setup blocker. This does not change activation, publication or readiness semantics.
- Red/green verification: seven tests failed on the reviewed implementation; all **38 focused tests / 172 assertions** pass after correction, including eight added cases and the stale-data safety case. Evidence: `evidence/D-21/review-red.log` and `review-green.log`. TypeScript, UI build and formatting/diff checks passed; logs use the same `review-` prefix. The earlier full regression and Chrome artifacts describe the initial delivery; neither matrix was rerun for this controller-only correction. Production activation remains off.
