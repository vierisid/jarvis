## Ownership and integration for Lapo / the next agent

`WorkflowCreationRoom` is an injectable body. `workflowCreationRegistration(useBinding)` exposes its room-local registration; it is deliberately not installed into the production registry yet. The default registry/legacy entry remain unchanged. Activate only with the authenticated F-07 provider, the shared host integration and D-33 release checks.

The host must:

1. Create one `WorkflowCreationController` above room navigation, keyed by authenticated account **and** vault/project. Supply `sessionCreationStorage(scopeId, sessionStorage)` or an equivalent scoped durable store. A bare project name shared across accounts is not a sufficient key.
2. Supply `createCompositionPort(() => currentCapabilities, authenticatedFetch)`. It checks the current F-01 capability before each request, uses the F-07 API, and bounds requests to 15 seconds. The host owns authentication and refreshing capability discovery. Missing/disabled/old capabilities cannot submit.
3. Keep the controller during room, sidebar and Pebble transitions. Call `dispose()` on logout or account/vault ownership change and retire the binding. Do not reuse a retired controller in another scope. Session storage preserves the prompt, pending request key, acknowledged result and recent selection/offset across a remount/reload in that tab. It is not a cross-device draft service; no arbitrary retention or user-data deletion is introduced.
4. Provide the recent `BriefViewPort` from canonical records. `readRecentWorkflows(authenticatedFetch, abortSignal)` reads the current workflow API, with four workers and an explicit 200-flow ceiling. It has no implicit interval. Cache/refresh above the room; abort and ignore stale responses on account/vault changes. Do not attach it to every render or the old eight-second polling loop. A future aggregate endpoint can replace this reader without changing the view.
5. The reader checks the latest run of each known flow, retrieves a name only for flows with runs and returns six recent rows. Missing/unreadable runs or an inventory over 200 flows produce an explicitly incomplete state, never a claim of complete global recency. This bounded fallback can require up to 405 reads at its ceiling; optimize with an aggregate API before enabling large-workspace polling. Captured step outputs never become UI summaries. `projectRecentWorkflows` can consume an already complete host snapshot instead.
6. Mount the body with the existing `BriefShellPort`. Successful composition navigates to `workflow-draft` with **both** returned `flowId` and `versionId`. Recent rows open `workflow` carrying its flow/version/run IDs. `See all workflows` targets `all-workflows`. The host owns those later room bodies and keeps the controller/view cached so Back restores the same prompt, selected row and offset.

The shared composer adds only optional sending/suggestion labels; chat defaults are unchanged. Its existing IME, UTF-8 bound, compact growth, focus, send morph and reduced-motion behavior are reused. The disabled ingredient entry is an explicit D-17 slot, not a fake attachment picker.

## Failure and truthfulness rules

- Persist a request ID **before** submitting. A duplicate press cannot start a second composition.
- A lost/invalid response leaves the original specification and request key pending. **Check request** recovers by ID; if absent it replays the same exact request. Edited text cannot silently replace an uncertain admitted specification.
- A terminal failed/blocked/cancelled receipt retains the prompt. An explicit later send creates a new request key, as F-07 requires.
- A successful receipt clears only an unchanged submitted prompt. Text edited during work survives. The opened-job acknowledgement prevents return navigation from immediately reopening the same draft; **Open draft** remains available.
- Storage failure blocks submission/navigation rather than risking a lost idempotency key. A failed initial read or validation also blocks every write to that record; edits stay in memory only. Restore session storage and reload the scope; no automatic clearing of uncertain state is offered. A later write failure after successful restoration retains the known request and can persist it once storage is writable again.
- Retirement during a recovery lookup prevents a subsequent replay POST, including when the lookup returns no receipt. Late receipts and failures cannot change the retired scope.
- Receipts must match request ID, exact prompt/name, job ID and valid result IDs. Blockers render as plain text. No raw transport error is displayed.
- `PAUSED` means waiting for a signal, not necessarily human approval. Failures, timeouts, quota/memory/schedule errors, stopped and unknown runs have distinct truthful copy. Test runs remain labeled. `SUCCEEDED` supports **Run completed**, not an inferred claim that a business goal advanced. Never-run drafts are absent from Recently run.
