# D-19 · Run history with one inline detail

Selecting a run now updates one inline inspection card. It never opens a second overlay or substitutes the latest run. The history distinguishes queued, running, paused, failed, cancelled, uncertain and succeeded, with step inspection, partial action receipts, waitpoints and recorded context available in the same card.

This is an optional, disabled Brief module on the approved unmerged D stack. The production room registry and legacy workflow route are unchanged. F-21 and authenticated host integration must be complete before activation. The preview uses illustrative in-memory data; Run workflow executes nothing.

## Implementation

`WorkflowViewHeader` shares the workflow name, action and navigation geometry with the actual D-18 editor. The active underline moves locally; reduced motion uses immediate placement. Canvas still retains rename, Save, Discard, Arrange, Undo and its dirty-navigation guard. Context remains the D-20 handoff in this preview.

`WorkflowRunsController` owns an account/flow/version-scoped history and selection by immutable run ID. Each selection clears the previous detail immediately. Aborted or late responses cannot replace the currently selected result, even when a provider ignores cancellation. A missing deep link remains missing rather than opening another run. Historical version IDs are retained and compared with the matching history record, not rewritten to the current editable version. Loading, empty, unsupported, unavailable and stale reads stay distinct.

List refresh rebuilds a contiguous prefix using fresh opaque cursors through the last loaded run ID, so new head pages cannot hide intervening runs. It coalesces overlapping polls and serializes refresh with explicit paging; the next eight-second tick never cancels a slow history or same-run detail read. Actual selection changes still cancel obsolete detail requests. Fresh details reconcile their matching history summaries, including protection against an older in-flight list snapshot. Refresh also updates older unselected rows. A refresh follows at most 20 pages; beyond that it marks the contiguous prefix partial and exposes its valid continuation. Failed or repeated-cursor gap reads preserve stale history for retry, rather than silently omitting rows. The selected ID and stored history/detail scroll positions survive ordinary room returns, chat and sidebar changes when the host retains the controller. Visible mounted rooms refresh read projections every eight seconds. Refresh never submits a command.

Manual Run is optional. While the supplied command is pending it is single-flight. A matching acknowledgement inserts and selects its exact returned run ID, then reads that run. Acknowledged runs stay visible exactly once while the history projection catches up; an unknown total stays unknown. An unconfirmed request stays locked through refresh and room remount. There is no retry, replay, resume or cancellation policy added here. A late acknowledgement cannot navigate an unmounted room. The host must persist/reconcile commands across full application reloads before supplying this port.

The card reads only an already-redacted presentation projection. Strings render as text, and fields explicitly marked redacted display `Redacted`. Receipt descriptions, partial effects, waitpoints and removed context remain inspectable. No raw error strings, effect arguments, credentials or bearer resume URLs are mapped by this module. The UI is not a substitute for server-side redaction.

History and detail scroll separately at desktop widths. Chat-open rows compact into two lines; the inspection remains inline and the workspace corner is reserved for Pebble. Below 450px available width, history and detail stack in the scrolling work area. Keyboard focus and reduced motion use the shared controls.

## PR review corrections

All three findings on reviewed head `76f71cc9` are repaired in this same D-19 branch:

- **R1, pagination gaps:** refresh walks the new cursor chain to the previously loaded tail. It no longer reuses an old continuation based on row count. Tests cover exhausted and partial history, a failed gap read/retry, repeated cursors and the bounded partial-prefix continuation.
- **R2, read starvation:** overlapping polls share one refresh; history and explicit paging share one sequential lane, and same-run details share an in-flight read. Slow reads complete instead of being aborted by the next timer tick. A deliberate selection or owner teardown still invalidates obsolete work.
- **R3, stale row status:** fresh selected detail updates that row's safe summary immediately. Refresh re-reads the loaded range so older unselected nonterminal rows also advance. A detail completed during a history read cannot be overwritten by that older snapshot; stale detail cannot overwrite fresh history.

The first seven regression tests all failed on the reviewed controller (`review-refresh-red.log`). After correction, 13 new regression tests and all existing Runs checks pass: **37 tests / 138 assertions** (`review-focused-tests.log`). Deferred promises explicitly simulate repeated polling while a read remains pending; these are concurrency tests, not measured live network latency. Six added boundary cases include partial refresh, repeated cursor, bounded continuation, detail/list ordering, stale detail and acknowledged-run projection lag. No new command, endpoint or production activation is introduced. This repair verification does not claim a separate independent re-review.
