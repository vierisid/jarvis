## State and actions

`OpportunitiesController` belongs to one authenticated scope and survives room unmounts. The selected proposal uses its ID, with the exact revision retained on every command. Reorder, refreshed content, theme/sidebar/chat changes and long content do not substitute another selected identity. A deep-linked `opportunityId` selects the actual matching proposal. Selection buttons are whole targets; passive paper and status do not imply extra navigation.

The optional port reads a **complete**, authorized collection. Ready, stale, loading, empty, unavailable and unsupported remain distinct. Approval requires the F-09 `canApprove` result plus the prepared identity, locked disabled workflow, current goal link, evidence, preview basis, readiness and bindings. Server-side readiness, authorization and effect handling remain authoritative.

Each decision captures proposal/revision/action and one idempotency key. It locks synchronously against duplicate or opposite decisions. A receipt must match the proposal, revision, decision and approved workflow version. Approval saved with pending/blocked registration is not displayed as Enabled and does not leave the room. A paused/changed/missing workflow is not represented as successfully enabled. Check result reads the original receipt; it never resends approval. Only a matching registered/enabled or dismissed receipt starts local acknowledgement and advancement.

Unknown transport results and malformed receipts retain the original proposal even if a refresh omits it. Definitive, adapter-certified refusal has a separate message; only a fresh read releases that failed attempt. A late response cannot steal a newer selection, typing focus or a retired account owner. Access revoked during refresh releases the visual refresh state while invalidating its pending response.

Acknowledgement holds the action targets still. Approval uses 520ms, dismissal 360ms, followed by a 160ms local content exit and 180ms settle. Only the resolved item is removed; another user selection remains selected. Reduced motion uses immediate placement. The next selection receives focus only if focus still belongs to the resolving actions. No removed tabs, date, subtitle, creation button or Authority Rules Apply footer returns.

4. Map `act` to F-10 POST `/api/brief/opportunity-actions/:proposalId/approve` or `/dismiss` with exactly `{revision, idempotencyKey}`. Persist the request before dispatch. The UI's returned receipt type structurally follows F-10; no import from its unmerged branch is required. Do not send extra flow IDs in the body or manually run the workflow. 5. Map recovery to F-10 GET for the original proposal receipt. Validate ownership and retain the captured request/version.
