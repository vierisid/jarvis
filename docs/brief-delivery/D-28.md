# D-28 — Authority without changing policy

D-28 adds an optional Authority room with the canonical 1–10 default level, all thirteen governed categories, explicit save feedback, and access to the existing advanced and emergency controls. The level follows the pointer continuously and snaps to an integer on release; keyboard arrows, Home and End use the same values. Off removes category membership and leaves the current level and override rules in force. It never grants permission.

The card is delivered for review, **not activated**. Merge prerequisite: D-01. Live activation requires integrated and verified **F-25** navigation, an authenticated host transport and both existing control destinations. Production registrations and capability defaults are unchanged. D-29 is outside this PR.

## Host integration and save semantics

`createAuthorityPort(scopeId, host)` reads the existing `/api/authority/status` contract and writes through `/api/authority/config` POST from A-15. The status envelope supplies canonical settings in `config` and current `EmergencyController` state in its top-level `emergency_state`; the engine config's startup emergency copy is not used for the banner. Disabled or malformed status never becomes a plausible default. The host supplies authenticated, scope-bound `request`, current write permission, explicit destination availability and an F-25 `navigate(destination, signal)` callback. Missing hosts return unsupported, missing destinations block live activation, and fixtures cannot enter the live shell. F-25 callbacks must honor cancellation before delayed navigation.

Retain one controller per authenticated scope across room remounts. Retire it on logout or replacement; a binding change also disables and purges the preceding controller. Never reuse a scope-bound transport for another account. Register through `authorityRegistration(useBinding)` only after `navigationCompatibility` and both advanced/emergency destinations are ready.

Edits remain visibly unsaved until **Save changes** is pressed. This explicit save row is a production feedback addition to the native control reference. It batches intentional changes rather than sending writes for every pointer movement. A save:

1. Reads canonical settings and detects changes to the fields being edited.
2. Sends only changed `default_level` and/or `governed_categories` fields, preserving additive category values and all advanced configuration.
3. Requires a successful `{ok: true, config}` acknowledgment and a fresh canonical read matching the edited fields before showing Saved.

A failed response can occur after the existing API has applied an in-memory change. Failed/lost acknowledgments, malformed receipts and failed/mismatched readbacks remain **not confirmed**, with no automatic replay. Edits stay visible but disabled until an explicit reload. Reload preserves the intended fields and offers **Retry save**, even when the server already reports those values in memory. Only an explicit retry sends them again; it still requires conflict preflight, successful acknowledgment and fresh matching readback. Unrelated fresh settings are preserved. **Discard retry** drops that intent and loads current values without claiming persistence or undoing any prior apply. A preflight conflict also requires reload. Read failures retain stale values with disabled editing and a visible error, including in read-only mode; permission loss removes them. Advanced and emergency navigation remains reachable during unknown saves and read failures.

The existing endpoint has **no revision/CAS contract**. Preflight comparison detects already-observed changes but cannot eliminate a concurrent write between that read and POST. This UI does not invent backend transaction guarantees. Full policy/entry-point certification remains Q-08's responsibility.

Polling and browser focus do not overwrite drafts or interrupt pointer gestures. During dirty, uncertain or conflicting saves, background reads refresh emergency status while retaining the policy baseline and draft; they never resolve persistence uncertainty or trigger a retry. Background refresh also defers while a room control has keyboard focus, so a read cannot blur it by briefly disabling writes. Every save still performs a fresh preflight read.

## Review corrections

All three review findings are fixed in the same PR #947:

1. Emergency status now follows the live status endpoint across pause, resume, kill and reset. Tests exercise a real isolated `EmergencyController` alongside an unchanged engine config copy.
2. An in-memory apply followed by failed persistence can be explicitly retried at the same value. Tests model separate in-memory and persisted levels, plus category retry, unrelated external changes, conflict after reload, discard, permission loss and forged confirmation.
3. Read-only status includes refresh errors. Recovery keeps write controls disabled; permission loss removes the settings.

The three regression cases failed against the reviewed implementation ([before-fix log](evidence/D-28/review-before.log)). It covers unchanged-value retry to confirmed save, pause/resume with unsaved edits, read-only stale error/recovery and explicit discard.
